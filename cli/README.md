# AirScan-QR 终端发送端（airscan-cli）

在**终端里**显示动态二维码的发送端：无需图形界面、无需浏览器，SSH 上来也能用。
手机打开 `../index.html` 的「接收」页用摄像头扫描即可接收。

协议 **v2.0**：帧载荷是二进制格式，**不再经过 base64**（省掉 33% 冗余）：

```
'B' | flags | tid(3) | nameLen | 文件名(UTF-8) | total(4) | idx(4) | 真实长度(4) | 原始大小(4) | 数据
       ↑ bit0 = 数据段是 zlib 压缩
```

- 多字节整数小端；数据段是**原始字节**——`|`、`\0`、任何字节都不会破坏解析；
- 数据段补足到 chunk 字节 → **各帧二维码大小完全一致**（末帧不再"小一圈"）；
- 接收端按"真实长度"截断，填充不进文件；原始字节通过 jsQR 的 `binaryData` 取；
- **自动压缩**：发送前先试 zlib，压完更小才用（`.7z`/`.zip` 这类会自动跳过）。
  文本/日志通常能压到 1/5~1/10，帧数同比减少；`--no-compress` 可强制关闭；
- 网页发送端发的是文本帧（`T|tid|name|total|idx|真实长度|原始大小|flags|base64`），
  接收端两种帧都认。

**兼容性**：v2.0 **不兼容旧协议**——发送端与接收端必须用同一版本（随包分发即可）。
接收端内联了 pako（纯 ES5 的 zlib 解压，老浏览器也能解压）和打过一处小补丁的 jsQR
（"AirScan patch"：字节段不是合法 UTF-8 时按原样返回，否则二进制载荷会整帧解不出来）。

## 平台支持

| 平台 | 渲染方式 | 说明 |
|---|---|---|
| Linux / Unix | ANSI 转义序列 | 任意终端；静态编译（musl），无 glibc 依赖 |
| Windows 真控制台（cmd / conhost） | Win32 控制台 API（`WriteConsoleOutputW`） | 用控制台属性画黑白块，**不依赖 ANSI/VT**（老 cmd 也能正常显示） |
| Windows 非控制台（Git Bash / mintty / 重定向到文件） | 自动退回 ANSI 渲染 | 与 Linux 同一路径 |

可执行文件本身的系统要求：Windows 版只依赖系统自带的 `msvcrt.dll`，
**Win7 / 8 / 10 / 11 直接可用**；Linux 版静态链接，无需任何运行库。

## 直接使用现成二进制

```
airscan-cli-win64.exe      # Windows x86_64，msvcrt 版，Win7+（119 KB）
airscan-cli-win32.exe      # Windows 32 位（PE32 i386），msvcrt 版，Win7+（124 KB）
airscan-cli-linux-x86_64   # Linux x86_64 静态可执行文件（108 KB）
airscan-cli-linux-i386     # Linux 32 位静态可执行文件（105 KB）
```

```sh
# Linux（按目标机器位数挑一个）
scp airscan-cli-linux-x86_64 user@老机器:~/
ssh user@老机器
chmod +x airscan-cli-linux-x86_64
./airscan-cli-linux-x86_64 要传的文件.zip
```

```bat
:: Windows（cmd 里直接跑；64 位系统用 win64，32 位系统用 win32）
airscan-cli-win64.exe 要传的文件.zip
```

## 从源码构建

```sh
# ---- Linux x86_64（musl 静态，产物无 glibc 依赖）----
apt install musl-tools    # 或 yum install musl-gcc
sh build.sh               # 脚本会先编 miniz（压缩库）再编主程序

# ---- Linux 32 位（i486/i686，静态，非 PIE）----
# 工具链：musl.cc 的 i486-linux-musl-cross（自带 gcc，无需安装到系统）
curl -LO https://musl.cc/i486-linux-musl-cross.tgz && tar xzf i486-linux-musl-cross.tgz
./i486-linux-musl-cross/bin/i486-linux-musl-gcc -c -O2 -DMINIZ_NO_ARCHIVE_APIS \
    -DMINIZ_NO_STDIO -Wno-type-limits miniz.c -o miniz-i486.o
./i486-linux-musl-cross/bin/i486-linux-musl-gcc -O2 -Wall -Wextra -std=c99 \
    -static -no-pie -o airscan-cli-linux-i386 airscan-cli.c qrcodegen.c miniz-i486.o

# ---- Windows（MSYS2，msvcrt 工具链，Win7 起可用）----
#   pacman -S mingw-w64-x86_64-gcc     # 64 位
#   pacman -S mingw-w64-i686-gcc       # 32 位
# 注意：miniz.o 必须按目标架构各编各的，不能混用
gcc -c -O2 -DMINIZ_NO_ARCHIVE_APIS -DMINIZ_NO_STDIO -Wno-type-limits miniz.c -o miniz.o
gcc -O2 -static -o airscan-cli-win64.exe airscan-cli.c qrcodegen.c miniz.o -lwinmm -lshell32
```

## 用法

```
airscan-cli [选项] 文件
cat 文件 | airscan-cli --name 文件名 -

  -f, --fps N      帧率 1-60，默认 8
  -c, --chunk N    单帧数据量（base64 字符数）16-2400，默认 200
  -n, --name NAME  接收端显示并保存的文件名（默认取路径文件名）
  -t, --tid XXX    任务号，默认随机三位
  -m, --mode M     half=半块字符（默认）| block=背景色方块（兼容更旧的终端）
  -s, --start N    从第 N 帧开始
      --once       每帧播一轮后退出（默认循环）
  -q, --quiet      不显示状态行与提示行
      --dry-run    只打印传输规划（帧数/二维码尺寸/预计耗时）后退出
      --cols/--rows N  手动指定终端尺寸（默认自动探测）
```

交互按键：

| 按键 | 作用 |
|---|---|
| `空格` | 暂停 / 继续（若输入缓冲里有没提交的半截内容，会先清掉再切换） |
| `,` `.` | 上一帧 / 下一帧（在补发模式下则在列表内前后移动） |
| `数字 + 回车` | 跳到指定帧 |
| **`帧号列表 + 回车`** | **进入补发模式**：如 `1,2,3,52,109`，也支持 `8,20-22` 区间（逗号分隔，从接收端复制粘贴后直接回车），只循环播放这些帧 |
| `f` 或 空回车 | 补发模式下恢复完整播放 |
| `q` | 退出 |

典型用法：

```sh
# 先看规划：会不会放不下、要多久
airscan-cli --dry-run big.tar.gz --chunk 300

# 正式发送
airscan-cli big.tar.gz --chunk 300 --fps 10
```

终端放不下时会**提前报错并给出建议的 --chunk 值**，不会糊成一团。

## 缺帧补发流程（与接收端配合）

接收端（手机浏览器）没收齐时，整套补发流程是：

1. 接收端点「**导出缺帧列表**」→ 拿到形如 `5,6,109` 的帧号（1 基，逗号分隔）；
2. **发送端不要退出**——回到正在播放的那个终端窗口，直接粘贴这串帧号、按回车：

   ```
   [12/522] 8.0fps 200c/f v9 输入:5,6,109
   → 回车后状态行变成： [补发 1/3] 帧5/522 8.0fps ...
   ```

   程序随即只循环播放这三个帧（顺序按你给的来，乱序也没关系）；
3. 接收端收齐后自动弹出下载；想停止补发、回到完整播放，按 `f` 即可。

要点：

- **必须在同一个进程里操作（不要退出重开）**：任务号是每次启动随机生成的，
  接收端靠它识别"新任务"——重开程序 = 换任务号 = 接收端会清空已收内容重来；
- **`--chunk` 必须与第一轮一致**——帧号按分帧算出来，改了 chunk 帧号就对不上；
  列表里的帧号超出范围时程序会当场提示，不会播错；
- 状态行会显示 `[补发 3/12] 帧52/522` 这样的进度（前者是列表位置，后者是总进度）；
- 帧号列表用**逗号**分隔（`1,2,3`）或区间（`8,20-22`）；**空格不要打进列表**——
  空格永远是暂停/继续键，输入到一半按空格会先清掉未提交的内容再切换暂停；
- 不在列表里的帧也可以用 `数字 + 回车` 单独跳过去补发。

## 验证状态（实测）

用项目自己的接收端解码库 jsQR 对**终端实际渲染结果**做了闭环验证：

- Linux x86_64 ANSI 路径：文本单帧、二进制 2048 字节 14 帧 —— 全部解码成功，
  **重组结果与原文件逐字节一致**；
- Linux i386（32 位）ANSI 路径：half/block 两种模式 + 单帧/14 帧 —— 全部通过，
  14 帧用例重组与原文件一致；
- Windows x64 / x86 ANSI 路径（重定向）：同上通过；
- Windows 真控制台路径（Win32 API 渲染，64 位与 32 位版都测了）：
  用屏幕缓冲抓取工具验证 —— 全部解码成功，**每帧数据切片与源文件精确匹配**，
  帧号正确滚动；**"刚好卡边界"的窗口**（所需行列数正好等于窗口大小）也能正常显示
  （曾出现"启动放行、渲染却报窗口太小"的矛盾，已按同一公式修正并回归）；
- **运行时补发模式**（在 PTY 里模拟真实按键验证，Linux x86_64）：
  - 输入 `1,2,3` 回车 → 只循环播放 1,2,3；
  - 输入 `2,4-6` / `2, 5, 9`（区间、逗号空格混合）→ 分别只循环 2,4,5,6 与 2,5,9；
  - 按 `f` 后恢复完整播放（从 4,5,6… 连续播下去）；
  - 越界帧号（如 `2,99`）当场提示、不退出；单个数字仍是跳帧（不误入补发模式）；
- **Windows 控制台按键路径**（用 `WriteConsoleInput` 向控制台注入按键验证）：
  空格暂停时画面保持不动、再按空格恢复播放、再按再停；
  修复过 `_getch()` 无键可读时阻塞导致"一按键就永久卡住"的问题；
- 接收端「导出缺帧列表」：模拟收 4/6 帧后导出，输出 `5,6` 与显示一致；
- **协议 v2.0（二进制帧 + 自动压缩）**，完整链路（渲染→jsQR→接收端→逐字节比对）全部通过：
  - 全 256 种字节值（10KB）：压缩到 355 字节，2 帧，**逐字节一致**；
  - 全 `|`、换行、`\0`（4KB）：压缩到 31 字节，**逐字节一致**（特殊字符完全无影响）；
  - 随机二进制（20KB，不可压缩）：自动跳过压缩，100 帧，**逐字节一致**；
  - 284KB 文本：压缩到 1KB，**6 帧传完**，逐字节一致；
  - 中文文件名 + 100 帧：接收端显示完整中文名，逐字节一致；
  - 网页发送端文本帧（27 帧）：收齐、文件名/大小正确、字节一致；
  - Linux x86_64 与 Windows x64 产物分别实测，结果一致。
- **协议 v1.1（末帧补足等长）**：14 帧用例**所有帧矩阵尺寸完全一致**（62×61），
  jsQR 解码后灌入接收端，**重组结果与原文件逐字节一致**；旧 5 字段格式仍被兼容；
- **中文文件名**：Windows（GBK 控制台）与 Linux 上分别用
  `很长的文件名_测试报告.docx` 实测 —— 参数编码自动还原成 UTF-8，
  接收端显示的正是完整中文名，14/14 帧解码、重组一致；
- **长文件名边界**：200 字符名 + `-c 200` → 载荷 420 字节（v13）正常；
  最极端组合（255 字符名 + `-c 2400`）载荷 2681 字节，仍在 v40 的 2953 之内。

## 已知限制

- **Windows 的运行库**：两个 Windows 版都用 msvcrt 工具链构建，只依赖
  `msvcrt.dll + kernel32.dll + winmm.dll`——这三个从 Windows XP 起就是系统自带，
  **Win7 / 8 / 10 / 11 直接运行**，不需要任何补丁或运行库。
  （如果改用 MSYS2 的 UCRT 工具链构建，产物会依赖 UCRT，Win7/8 就需要
  KB2999226 补丁——所以这里特意选了 msvcrt 版。）
- **32 位系统**：已提供 `airscan-cli-win32.exe`（32 位 Windows）和
  `airscan-cli-linux-i386`（32 位 Linux，静态非 PIE）。
- **Linux 老内核**：静态 musl 产物无 glibc 依赖，理论上 CentOS 6（内核 2.6.32）
  及以上可运行；更老的内核（CentOS 5 / 2.6.18）未实测。
- **文件大小上限 256MB**：屏幕→摄像头链路的实际速率只有几 KB/s，更大属于误用；
  超过会直接报错（同时保护 32 位构建的内存边界）。
- **接收端仍需浏览器**：终端程序只能"显示"，不能"扫描"。

## 源码说明

| 文件 | 作用 |
|---|---|
| `airscan-cli.c` | 主程序（C99，POSIX + Win32 双平台） |
| `qrcodegen.c/h` | 二维码编码器，[Project Nayuki](https://www.nayuki.io/page/qr-code-generator-library)，MIT License，原样引用未改动 |
| `build.sh` | Linux 构建脚本（优先 musl 静态） |

编码器使用 ECC 级别 L（与网页发送端一致），并开启 `boostEcl`：在不增大版本的
前提下自动提升纠错等级，等于白送一部分容错。

扫码建议：终端字体调大、关闭反色/透明背景主题、保持二维码四周静区不被裁切。
